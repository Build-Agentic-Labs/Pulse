## 🔴 CRITICAL

### 1. Per-project RLS isolation hole on `manufacturing_components` & `document_type_codes` — [3x corroborated + hand-verified]
**Files:** `supabase/migrations/20260527193000_add_manufacturing_nomenclature.sql:77–219`; gap is the absence in `20260601124000_per_project_rls_isolation.sql`.
**Problem:** Migration `124000` rewrote 13 tables to gate on `has_project_access(...)`, but these two tables (added later, in `27193000`) still gate only on `workspace_members` membership — any role, any project. A workspace member explicitly granted `none` access to a project via `project_access` can still **read and write** these rows for that project by calling PostgREST directly. This is the exact gap `124000` was written to close; it just missed these two tables.
**Risk:** Per-project access control is bypassable for component and document-code data — a real data-isolation defect, not theoretical.
**Fix:** New migration `20260601125000_per_project_isolation_components_and_codes.sql` that `DROP POLICY` + recreates all 8 policies using `public.has_project_access(public.scenario_project_id(scenario_id), 'view'|'edit')`, mirroring the stations/zones pattern in `124000`. Add both tables to `scopedTables` in `scripts/apply-per-project-rls-migration.mjs` post-checks.
**Regression guard (recommended):** a test asserting every RLS-enabled data table's policies reference `has_project_access` — prevents the next late-added table from silently slipping outside the model.

### 2. Full Gantt save runs 10–20 sequential writes with no transaction — [2x corroborated]
**File:** `src/domain/supabase-planner.ts:1852–1981` (`savePlannerStateToSupabase`), `1983–2101` (`savePlannerShellToSupabase`).
**Problem:** The save is a sequence of independent, auto-committed PostgREST calls: upsert products → scenarios → stations → zones → delete stale tasks → upsert tasks → delete/insert dependencies → delete/insert steps → parts → events. A failure mid-sequence (network, RLS, server error) leaves the project partially written — e.g. old steps deleted, new ones not inserted.
**Risk:** Permanent corruption that a retry can't fix (read-then-save recomputes a different diff). Highest blast-radius reliability issue.
**Fix:** Wrap the save in a Postgres function invoked via `.rpc()` (single `BEGIN…COMMIT`). Minimum viable: make each delete+insert pair atomic.

## 🟠 HIGH

### 3. `assertTaskInProject` — 3 sequential round-trips per write, redundant with RLS — [2x corroborated]
**File:** `src/domain/supabase-planner.ts:915–934`.
**Problem:** tasks → scenarios → products, serially, before nearly every write; runs once per task inside `saveTasksToSupabase`'s `Promise.all` (100 tasks ≈ 300 RTTs of latency). The check duplicates what RLS already enforces server-side.
**Fix:** Collapse to a single join query/RPC, or remove it for authenticated paths and rely on RLS.

### 4. Non-atomic delete & reorder — [2x corroborated]
**Files:** `deletePlannerTask:2520–2528`, `reorderProcedureSteps:2310–2319`.
**Problem:** `deletePlannerTask` manually deletes dependency edges then the task in separate calls — but `task_dependencies` already has `ON DELETE CASCADE`, so the manual step is redundant **and** opens a split-brain window (edges gone, task remains) visible to realtime subscribers. `reorderProcedureSteps` issues N separate UPDATEs → partial failure = visible sequence corruption + N spurious realtime re-renders.
**Fix:** Delete the task directly and let CASCADE handle edges. Replace reorder with a single batched `UPDATE … FROM (VALUES …)` RPC.

### 5. Hardcoded personal email seeded into migration history — [2x corroborated]
**Files:** `20260601120000_add_platform_superadmin.sql:77`; `20260522143000_add_workspace_access_grants.sql:94–97`; post-check in `scripts/apply-user-access-migrations.mjs:115`. Also hardcoded IDs `workspace-default` / `project-flexboost` in `20260518231500:50–72`.
**Problem:** `rlopez@anacorp.com` is pinned permanently in git history and asserted by an applier; the hardcoded workspace/project IDs break clean staging/CI seeding.
**Fix:** Move seed data to an env-specific `seeds/` script outside migration history; make the post-check generic (`count(*) > 0`).

### 6. `tool_library` global rows (`project_id IS NULL`) — read leak + broken insert — [2x corroborated]
**File:** `20260525233000_harden_storage_and_tool_policies.sql:115–133` (+ storage policy `:40–48`).
**Problem:** Global tools are readable by **any** authenticated user (cross-tenant leak if a second org is ever added), and the storage policy extends that to the underlying image objects. Conversely, **inserts** of global tools are silently RLS-denied, so `uploadToolLibraryImage` / `upsertToolLibraryMetadata` throw at runtime when no project context exists — global-tool management is quietly broken.
**Fix:** Scope global tools to workspace membership for reads; add an explicit insert policy (superadmin or active member).

## 🟡 MEDIUM

### 7. RLS functions called bare instead of `(SELECT fn(…))` — [2x corroborated]
**Files:** policy bodies across `20260518231500`, `20260521120000`, `20260525234000`, `20260527193000`, etc.
**Problem:** `has_workspace_role(...)` / `has_project_access(...)` / `auth.uid()` called directly in `USING`/`WITH CHECK` are re-evaluated **per candidate row**. On hot tables (tasks, steps) this is the biggest latent perf cost as data grows.
**Fix:** Wrap in `(SELECT …)` so Postgres evaluates once per statement. Mechanical, low-risk.

### 8. `search_path = public` instead of `''` on all 22 SECURITY DEFINER functions
**Problem:** Defense-in-depth gap — a `public`-schema object could shadow an intended one. Low exploitability on a hardened Supabase project, but the recommended hardening is `set search_path = ''` with fully-qualified references (most already use `public.` prefixes).

### 9. `select('*')` + unbounded fetches
**Files:** `actual_events` load `:1774` (append-only, never capped); superadmin all-workspaces/projects load `:1362–1363`.
**Fix:** Add `.limit()`/pagination on `actual_events`; column-prune the superadmin loads. Optional `actual_events(task_id, timestamp DESC)` index for most-recent-first paging.

### 10. N+1 in batch saves
**Files:** `saveTasksToSupabase:2109` (`syncStepToolsForTask` per task), step-tools existence reads.
**Fix:** Batch existence reads with one `.in(taskIds)` then group in JS; batch upsert/delete.

### 11. `.or()` filter strings interpolate raw IDs
**Files:** `supabase-planner.ts:1763, 1877, 2008, 2392, 2492`.
**Problem:** Raw ID interpolation into PostgREST `.or()` strings. Real risk is low (IDs are UUIDs / sanitized via `safeStorageSegment`) but there's no server-side guard.
**Fix:** Prefer typed `.eq`/`.in`; if `.or()` is required, assert `/^[a-zA-Z0-9_-]+$/` first.

### 12. Lost-update window in `saveManufacturingStepToSupabase`
**File:** `supabase-planner.ts:2166–2192`.
**Problem:** Reads existing steps, merges, re-upserts — without using the existing `version` column for optimistic concurrency. Concurrent edits silently lose updates.
**Fix:** Route single-step saves through `upsertProcedureStep` (which checks `version`) or add `eq("version", expected)`.

### 13. No `schema_migrations` ledger
**Files:** `scripts/apply-*-migration.mjs`.
**Problem:** Custom appliers commit DDL directly and write nothing to Supabase's migration ledger, so `supabase migration list` / `db push` have no knowledge of `20260601120000–124000`. Risk of environment divergence and future `db push` conflicts. (Mitigated today by the SQL's own `if not exists` / `or replace` idempotency.)
**Fix:** After each apply, `supabase migration repair --status applied <version>`, or fold these into the standard `db push` flow with guard blocks.

## 🟢 LOW — Schema modeling debt (design discussion, not bugs)
- **Relational data stored as blobs:** `products.custom_fields`/`tasks.custom_fields` (jsonb) despite a typed `custom_columns` table; `manufacturing_steps.dependency_ids text[]`; `stations/tasks.tools_required text[]` despite `tool_library`/`step_tools`. No FK integrity, hard to query/report. Biggest long-term smell.
- **Text-cast UUID PKs** (`gen_random_uuid()::text`) everywhere — works, but wastes bytes per FK/index entry and fragments B-trees vs native `uuid`. Not worth migrating now.
- **Dual-nullable-FK CHECK gaps:** `document_type_codes` and `custom_columns` allow "both FKs set", bypassing partial-unique/scoping logic. Add exclusivity CHECKs.
- **Empty-string defaults** (`name`/`instruction` default `''`) allow meaningless rows to persist; add `CHECK (col <> '')`.
- **`actual_events` is mutable but has no `updated_at`** — for a manufacturing event log, decide append-only (drop UPDATE policy) vs add audit timestamp.

## ✅ Genuine Strengths (verified)
- **No service-role key in client code** — `service_role` confined to `scripts/`; only `SUPABASE_URL` + `ANON_KEY` are `NEXT_PUBLIC_`.
- `throwIfError` wrapper → no silently-swallowed errors in normal data paths (storage signing is the one exception, M-6 in source review).
- **Correct N+1 avoidance on scenario load** — all child tables fetched via one batched `.in(taskIds)`; composite indexes are `task_id`-leading.
- **Optimistic concurrency** (version column) with retry-merge on the key update paths.
- `maybeSingle()` used correctly throughout; Supabase client is a proper singleton.
- Composite index ordering consistently equality-first, range-second.
- `platform_admins` has no user-facing write policy — no self-promotion to superadmin; MVP open/anon policies fully superseded.
- All timestamps are `timestamptz`; all quantities/durations are `numeric` (no float rounding in takt/cycle math); `set_updated_at` trigger applied consistently and idempotently.

## Recommended Remediation Order
1. **#1** (isolation hole) — pattern confirmed, isolated to one new migration. Ship first.
2. **#5** (strip hardcoded email/IDs from migrations) — quick, unblocks clean staging.
3. **#2 + #4** (atomicity) — fold multi-row writes behind a few `.rpc()` functions; fixes corruption *and* the per-row RLS/latency costs together.
4. **#3 + #7 + #10** (latency: redundant checks, per-row RLS, N+1).
5. **#6, #8, #9, #11, #12, #13** as a hardening pass.
6. **#14** schema modeling — separate design discussion; not urgent.

> Architectural note: findings #2/#3/#4/#7 share one root cause — the app treats the DB as a stream of REST calls rather than transactions. The systemic fix is not 20 patches but moving multi-row writes behind a handful of transactional RPCs, which addresses atomicity, per-row RLS overhead, and latency simultaneously.
